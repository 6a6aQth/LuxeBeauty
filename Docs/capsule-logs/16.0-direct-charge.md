## Key Changes

The booking page stays on the site. The server charges MWK 100, ignores any browser amount, and stores a new charge id as `Booking.ticketId`. Success comes only from `GET /mobile-money/payments/{chargeId}/verify`. That path marks the booking successful, applies the 30% flag, sends SMS, emails the ticket when an email exists, and returns the ticket for the existing PNG download.

## Architecture Decisions

- Loyalty is calculated on the server at confirm time. It is not sent as PayChangu metadata, because the Direct Charge initialize body in the guide has no meta field.
- Admin force-verify still calls the hosted `verify-payment` URL. That is out of scope for this capsule.

## Deviations from SDD

- FR-03 says the loyalty flag is also sent to PayChangu as metadata. Initialize uses only the documented Direct Charge fields.
- The booking copy shows MWK 100, the amount actually charged, until 16.8 restores K10,000.
