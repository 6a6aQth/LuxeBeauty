## Key Changes

Password sign-in reads `neon_auth."user"` and `neon_auth.account` for that email and returns “This email uses Google. Continue with Google.” when the only provider is Google. It does not call Neon sign-in, so no session and no credential are created. A wrong password on a credential account stays a normal sign-in failure.

Sign-up refuses an email that already has a `CustomerProfile` or a Neon user, including a Google sign-in that has not saved a phone yet. The password is entered twice. The server rejects a mismatch, then sends one password to Neon Auth. The app database still has no password column.

If a later Google session’s email already belongs to a `CustomerProfile` with a different Neon user id, `/auth/continue` signs that session out and does not show the phone form. `complete-profile` does not insert a second row. When Neon links the verified Google email onto the existing user, the profile lookup by `neonUserId` still sends them to `/account`.

## Architecture Decisions

- Identity is read from `neon_auth` with a parameterized query that selects `providerId` only.
- The client page compares the code `email_already_has_account` locally so the continue page does not import Prisma.
- Neon’s default account linking is what keeps a password user and a later Google sign-in on one Neon user. The app guard only stops a second studio profile if that link does not happen.
