# Capsule F1.0 — False “Time Slot Unavailable” toast after a successful payment

- **Created:** 2026-09-26
- **Type:** Fix
- **Branch:** `fix/F1.0-false-slot-unavailable-toast`
- **Status:** Implemented. Tests deferred.
- **SDD Sections:** FR-09 (slot availability), FR-14 (ticket display), NFR-05 (booking page polls successful bookings)
- **Source Entry:** Reactive Log `F1.0` in `/Docs/workstream.md`
- **Dependencies:** Capsule 16.0. Success stays on `/booking` and sets `step` to `ticket`. The 1-second poll of `/api/bookings?status=successful` is unchanged.
- **Security-relevant:** No
- **Priority:** High

## Diagnosis

`app/booking/page.tsx` polls successful bookings every second and passes booked times plus admin blocks into `BookingForm` as `unavailableSlots`. `components/booking-form.tsx` clears `formData.timeSlot` and shows a destructive toast whenever that list contains the selected time.

After PayChangu verify marks this booking `successful`, the next poll includes that date and time. The form still holds the same `formData.timeSlot`, so it treats the customer’s own booking as a lost slot. The ticket reads `ticketDetails`, so “Appointment confirmed” and “Time Slot Unavailable” render together.

The warning is still correct while `step === "form"` and another booking or an admin block takes the selected time.

## Implementation

`components/booking-form.tsx` returns from the unavailable-slot effect when `step` is not `"form"`. Payment, awaiting, failed, and ticket no longer clear `formData.timeSlot` or raise the toast. Going back from payment to the form still warns if the time is now booked or blocked.

Moving from the form to payment does not create a booking and does not occupy the slot. The pending row is created when Pay starts. The calendar only treats `successful` bookings and admin `UnavailableDate` rows as taken. Checkout checks that the time is a valid weekday slot. It does not reject an admin block or an existing successful booking. Confirm does not either.

Out-of-scope recommendation: reject checkout and confirm when the slot is admin-blocked or already successful. That belongs with roadmap 13.1, not this toast.
