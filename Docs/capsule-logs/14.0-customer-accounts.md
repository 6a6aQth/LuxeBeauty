## Key Changes

Optional Neon Auth sign-up and sign-in, including Google. A `CustomerProfile` stores name, email, and phone. Guests still book with no session. Signed-in checkout writes profile name, phone, and email on the server. `/account` lists upcoming and past successful visits for that phone and shows loyalty progress. Upcoming visits download the confirmation ticket. Account reschedule uses the existing once / 24-hour / no extra payment rules and rejects a booking whose phone is not the session phone.

A first Google sign-in collects name, email, and phone on `/auth/continue` before the profile exists.

## Architecture Decisions

- Neon Auth holds the password. The app table is `CustomerProfile`, matched by `neonUserId`. No foreign key on `Booking`.
- `getNeonAuth()` stays null until the base URL looks like a real Neon Auth URL and the cookie secret is at least 32 characters. Guest checkout does not call Neon Auth unless `useSession` is set.
- Visit past/upcoming uses Africa/Blantyre as UTC+2.
- `prisma db push` was run after `DATABASE_URL` was added. The Neon database is in sync with the schema.
- Phone storage is canonical E.164 after capsule 15.0. This capsule no longer stores the phone exactly as typed.
